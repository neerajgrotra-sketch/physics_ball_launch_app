# Bank Shot

A bounce-puzzle game. The player launches a steel ball, choosing angle and power, and places a few bars
wherever they like so the ball ricochets into a glass barely wider than itself. **Bounces are true
reflections** off the bars, the glass, the floor and all four board edges (the floor and edges a little softer
than a bar, so a stray ball settles). **A win uses every bar:** all of the level's bars must be placed and the
ball must bounce off each one before it settles in the glass (2 bars, both; 3 bars, all three). Every level is
generated with a stored solution that does.
The last few launch paths stay on screen as fading ghost trails, so each try teaches the next.

Target platform: iOS first, built with Expo (React Native) and @shopify/react-native-skia for the board.
`reference/prototype.html` is the working browser prototype. It is the source of truth for feel,
visuals and controls. Open it in a browser before building any screen. Deliberate differences: the game's
floor and edges bounce (the prototype's are dead), glasses are open with no hood, levels give up to 3 bars,
and the "win uses every bar" rule. The look reference for long multi-bounce chains is a SimLoop clip the owner shared.

## Rules that must not break

1. **Physics stays pure.** `physics/` must not import React, Expo, Skia, or anything platform-specific.
   No `Math.random`, `Date`, or `performance` inside it. The game, tests and solver all call the same code.
2. **Fixed timestep.** The simulation steps at `DT = 1/240` s, independent of frame rate. The UI never
   steps physics per frame. It calls `simulate()` once per launch, gets the full path, then plays the path
   back at 120 points per second (`recordEvery = 2`).
3. **Determinism is a feature.** The same level, pieces, angle and power must always give the same path.
   Ghost trails and "so close" moments only mean something because of this. The determinism test guards it.
4. **Every level needs the bars, and every level has a stored answer.**
   - Every bar, every time: by rule, in `simulate()` a win needs all of the level's bars placed and touched
     (`skipped` otherwise, with `touched` saying which were hit).
     `findDirectShot()` still sweeps every 0.1 input with no pieces as a guard on that rule.
   - Stored answer: each level JSON has a `solution` (piece positions in whole units, rotation in whole
     degrees, angle and power on the 0.1 grid) that bounces off **every** bar the level gives
     (`usesEveryBar()`). The Solve button places those pieces, sets the values and launches. Tests check
     it is a legal placement, lands, and uses every bar.
   - Par: each level JSON has `par`, the fewest bounces the solver found for a win, and the stored
     solution takes exactly that many (a test checks it). `findSolution()` builds many chains and keeps the
     fewest-bounce one that is still forgiving (`MIN_ROBUSTNESS`).
   - Never hand-edit level JSON. Change designs in `tools/design-levels.ts` and run it. `findSolution()`
     builds chains bar by bar along the ball's path, then picks the most forgiving launch for one.
5. **Tunnelling.** At 240 Hz and max speed 1120 px/s the ball moves about 4.7 px per step, under its 8 px
   radius. If max speed goes up or the radius goes down, add substeps so the per-step distance stays
   under the radius. The glass tunnelling test catches regressions.

6. **Cross-engine determinism.** iOS runs Hermes, while the tools run on Node (V8). `Math.sin`/`Math.cos`
   can differ in the last bit between engines. Stored solutions are chosen to be forgiving (neighbouring
   0.1 inputs land too), which absorbs this. Still, add an on-device check that runs every level's solution
   in a dev build.

## Coordinates and units

- The world is 400 × 560 logical units (`WORLD`), y pointing down, floor at y = 540, launcher at (44, 512).
  (The prototype is 400 × 720; the game is shorter so the board fills a phone's width under the controls.)
  Scale the board uniformly to fit the screen. Never change world units to fit a device.
- Angle is in degrees (0–90), adjustable in 0.1 steps. Power runs 0–100 and maps to 280–1120 px/s
  through `speedFor()`.
- A placed piece has a centre (x, y), rotation `deg` in whole degrees, and length `len`.

## Gameplay behaviour to match the prototype

- **Aim:** drag out from the launcher. Direction sets the angle and distance sets the power. Grabbing the
  dotted aim line is a rubber band: the dot you took stays under your finger, so round the launcher sets
  the angle, in or out sets the power, and nothing else drifts (`grabAimLine`/`swingTo` invert the
  launch velocity from the dot's position).
  Bars on the board take a touch first. The −/+ buttons beside each slider nudge by 0.1.
- **Aim preview:** only the first 0.3 s of free flight is shown, with no bounce prediction. Bounces are
  the puzzle, so never preview them.
- **Pieces:** bars are named Bar 1, 2, 3 (tray chips and board labels). Tap a tray chip to place a bar, drag
  it to move. The selected bar has a dotted lever out of one end with the rotate icon at its tip
  (`leverLine`, 60 long): drag anywhere on it to turn the bar about its centre, finger clear of the bar.
  Two dotted arms out of its centre (`moveArms`, one along x, one along y, each with a two-way arrow grip) slide the bar along
  that axis from a distance; dragging the bar itself still moves it freely.
  Tapping the other end (small ring) moves the lever there; on selection it goes on whichever end keeps
  its tip on the board (`leverEnd`). While a bar is selected the aim rows become its rotation
  controls: a 0–179° slider, −/+ 1° nudges (hold to repeat) and a small Remove button (a bar can also be dragged down past
  the floor to remove it). A cannon chip beside the bar chips switches back to the aim sliders (so does touching the cannon or its
  aim line); tapping the selected chip deselects it. Launching keeps the selected bar selected. An undo button before
  Launch steps the bars back (game/history.ts: each change is a step, a drag or held slider is one, 30 deep; not during a shot). Bars must keep a ball's width (18) from the glass, walls, launcher and each other
  (`game/placement.ts`, the same rule the level generator uses): a bar dragged somewhere it isn't allowed
  turns red and snaps back to its last allowed spot on release; rotation skips clipping angles; a new bar
  lands on the nearest allowed spot. Pieces can't be edited mid-flight. (The prototype removed a bar by re-tapping its chip.)
- **Trails:** keep the last 4 launches, oldest faintest. A successful trail is drawn in red.
- **Skip:** during a flight, a tap on the board, a touch on the angle or power controls (or Launch, which reads "Skip ›") jumps to the end of the
  shot. The path is already computed in full, so the whole trajectory becomes the trail and the outcome
  counts exactly as if watched; only the remaining bounce sounds are dropped (`usePlayback().skip`).
- **Bounces:** bars (restitution 0.85), the glass and its plate, and the floor and four edges
  (`WALL_RESTITUTION` 0.7, with a little friction so a rolling ball stops). A shot ends when the ball
  settles in the glass, comes to rest, hits a dead grey surface or a hazard (it bursts, no popup) if a level has one, or runs out of time
  (14 s). Landing without every bar placed and hit says so and names any bar it missed (`skipNotice`).
- **Dead hits:** when a shot hits a dead surface, mark the spot with a small red ×.
- **Win:** the ball has to settle inside the glass for 0.35 s. Show "In the glass in N tries", then
  unlock the next level and save progress locally.
  After a win, Launch becomes "Watch again ▶": it replays the winning shot exactly (bars restored to where
  they were, same angle and power) without resetting or counting a try. The card's left button is
  "Start over" (or "Try it yourself" after Solve), which resets the level. Any edit after a win (touching the board, a
  bar chip, a slider or rotation) or the card's ✕ closes the card and goes back to normal play, keeping bars,
  trails and tries; the level stays won.
- **Score (golf):** every real bounce counts (bars, edges, floor, outside of the glass), except down inside
  the glass (`SimResult.bounces`, `Hit.counts`). A live counter on the board ticks up during the shot
  ("N bounces / par P"), and the goal line under the board reads "Goal: into the glass in P bounces, off all N
  bars". A win names the result (Eagle, Birdie, Par, Bogey…), gives 1–3 stars (3 at par or better, 2
  within two) and points (`game/score.ts`); each level's best is saved and the level list shows stars and a
  total. Wins with a hint or Solve unlock the next level but earn no stars or score (kept clean for a
  future verified leaderboard: physics is deterministic, so a server can re-run a submitted shot).
- **Help (the Solve button):** opens a card offering a hint (places the next bar where the stored solution
  has it; clashing bars go back to the tray) or the full solution. Each sits behind a rewarded ad
  (`components/ads/RewardedAds.tsx`; a 5-second placeholder until AdMob is wired into a store build).
  Using either marks the round as helped until Start over.
- **Solve:** places the stored solution's pieces (unused pieces go back to the tray), sets angle and power,
  and launches. The win card then reads "Here's one way in", with "Try it yourself" (resets the level) and
  "Next level". The card sits at the top of the board so the solution path stays visible.

## Level design

Levels live in `tools/design-levels.ts` (geometry), then `npx tsx tools/design-levels.ts <id-prefix>` finds the
stored solution and par (a few minutes per level). A spiked edge on a block is a thin hazard laid along that edge (hazards are drawn under blocks, so only the outer spikes show). Optional extras on a level: `blocks` (fixed solid rectangles
the ball bounces off, softly like the walls; bars keep a ball's width clear of them, the same rule as for
the glass) `hazards` (spiked red rectangles, same shape as blocks: touching one, out to the tips of its spikes, destroys
the ball and ends the shot as "dead"; bars keep clear of them like any obstacle) `pads` (spring pads: same shape as blocks, but they throw the ball back at 1.3× plus a 240 px/s kick along the normal, capped at 1120 px/s; like bars, a win needs every pad touched) and `fixed` (plain dead segments). Next worlds are listed in `BACKLOG.md`.

## Screens and navigation

- **Tutorial** (`levels/00-tutorial.json`, "Learn the ropes": a real level with three bars, level 1 in the
  list; `game/coach.ts`, `game/tutorial.ts`): a new player goes straight into it from the levels screen (and tapping its card, or ⚙ "Replay the tutorial",
  starts the guide again; Start over / Try it yourself afterwards gives the plain level), and
  a ghost finger (`components/coach/GhostFinger.tsx`) leads them through the level's stored solution, one
  step at a time, each step waiting for them to actually do it: place each bar, then for each bar drag it
  onto its dashed outline (drawn on the board) and turn it to match (tap it, drag its handle), then set the
  angle and the power (each step's finger alternates between the two ways: the dotted line, and the
  slider; either is accepted for either), then launch. A bar dropped or turned near its outline, and an aim let go near the answer, snaps
  onto it (on release only: changing a slider's value under the finger sends it running), so the guided shot always lands. The plan is derived from the board each time (undo something and
  that step returns), and a hint on screen is dropped the moment it isn't for the current step
  (`stepKey`), so it can never nag about something already done and the finger appears after 1.5 s without a touch (no step counter: players disliked it). The
  win is marked assisted (no stars or score), and the tutorial level never scores however it is played (replayed
  shots, "Try it yourself": no stars, points or best) and its Solve button just solves it, with no ad. It runs once: "Skip tutorial" on the caption, finishing it, or
  Tips off in settings ends it for good; ⚙ has "Replay the tutorial".
- **First-bar hint:** on every other level, the finger only shows Bar 1 to place, after 4 s idle with
  nothing on the board, and not on a level already won. "Stop tips" on its caption, or Tips in ⚙, turns it
  off for good (`components/coach/Tips.tsx`, remembered). Any touch hides the finger and restarts the clock.
- Web sliders (`@react-native-community/slider`) cache their page position from first layout and only
  re-measure on a window resize, so `AimControls` sends that resize at the start of each touch on a slider
  (it was reading touches from the wrong place when first laid out mid-screen-transition).
- Moving a bar so its turn handle's tip would hang off the board puts the handle on the bar's other end.

- **Levels screen** (`app/index.tsx`): two-column cards (a finished tutorial shows "Tutorial ✓" and its winning shot, not a lock). Won levels and the next one to play show a drawing
  of the level (launcher, glass and, once won, the player's last unassisted winning shot (`components/levels/ShotThumbnail.tsx`, SVG, re-simulated from the stored
  inputs in `game/shots.ts`), the level's number and name, best stars and bounces; levels further on show
  a big number and a lock (only a look while `LOCK_LEVELS` is off). The next level is highlighted.
  A won card has a Replay button: it opens the level with that shot's bars and aim set up
  (`/level/[id]?replay=1`, `shotSlots`) and plays it once, unscored, then the player carries on from there. Header total score.
- **Level header:** ⚙ (settings sheet: music, version) and ••• (back to the levels, also from a deep link)
  on the left, level name in the middle, ‹ › on the right. No back arrow.
- Level locks exist but are off while levels are tested (`LOCK_LEVELS`). Planned work is in `BACKLOG.md`.

## Visual identity

The look is engineering graph paper in light mode and a blueprint in dark mode, with
Barlow and Barlow Condensed type. Use the colour tokens from `reference/prototype.html` (`--paper`,
`--grid`, `--ink`, `--pencil`, `--red`, `--muted`, `--steel`) and follow the system appearance setting.

## Launch and intro

- Launch screen (iOS/Android, expo-splash-screen in `app.json`): the rounded icon `assets/splash-icon.png`
  (made by `scripts/make-icons.mjs`) centred at 150 pt on the panel colour, light and dark. The web page
  (`public/index.html`) shows the same thing while the game loads.
- Then the intro (`components/splash/Intro.tsx`, timeline in `introPath.ts`) opens on that exact picture,
  so the handoff is seamless, and plays the app's idea once in ~2.7 s: graph paper, the ball launches, banks
  off a bar into the glass, the title drops in, then a "Let's go" button with the version under it. The shot plays the launch, bar and glass sounds. It waits there (no auto-advance, so
  the title can be read); "Let's go" or a tap anywhere opens the levels. A tap mid-animation jumps to the
  finished picture. Every cold start; reduced motion just fades in.
  Built with plain Reanimated views (no Skia), one clock driving every frame. Expo Go shows its own launch
  screen; the real one appears in development and store builds.

## Versions and sound

- Version: `package.json` and `app.json` (`expo.version`) stay equal; record changes in `CHANGELOG.md`.
  Store builds bump `expo.ios.buildNumber` / `expo.android.versionCode`. The level list shows the version
  and the git commit (`components/version.ts`; Vercel passes `EXPO_PUBLIC_COMMIT`).
- Music: one looping track per level, mapped in `components/feedback/music.ts` (files in `assets/music`);
  levels without their own track play level 1's (`trackFor`). It starts when the level opens.
  A header ♪ button turns music on/off (remembered). Effects are generated by `scripts/make-sounds.mjs`.
  On web, audio starts on the first tap anywhere (browser rule; the tap that opens a level counts) and runs
  through one Web Audio context (`components/feedback/webAudio.ts`). Sound plays with the iPhone silent
  switch on (native `playsInSilentMode`; web `navigator.audioSession.type = 'playback'`).

## Commands

- `npx vitest run`: physics and level tests. Run them before every commit.
- `npx tsx tools/report.ts`: full no-direct-shot proof plus how forgiving each solution is (about 1 min per level).
- `npx tsx tools/design-levels.ts [id-prefix]`: regenerate level JSON after changing geometry.
- `npx tsx tools/needs-walls.ts <id prefix> [samples] [seed]`: how many of a level's bounces are off the floor or board edges,
  and whether any answer exists when those are deadly (`Level.edgesDead`, analysis only). Use it for wall-bank levels.
- `npx tsx tools/assess-levels.ts [samples] [level index]`: difficulty numbers per level (bars, obstacles, par, how forgiving
  the answer is, hazard deaths, and "found": random bar-chains the solver finds per 10,000 tries, lower = harder to stumble
  on). Run it after adding a level and keep the curve rising (see BACKLOG.md). Pass a level index to run one level alone,
  e.g. in parallel.
- `npx tsc --noEmit`: typecheck.
- `npm run play`: build the static web site and serve it at http://localhost:8090 (stable, fast, deep links work).
- Deployed on Vercel from GitHub (`vercel.json`): every push to `main` rebuilds the site. `public/index.html`
  is the web page template (phone fit, no zoom, Add to Home Screen); `scripts/make-icons.mjs` draws the icons.
- `npm run web`: Expo dev server for working on the web build. `npm run build:web` exports a static site to `dist/`.
  Both first copy `canvaskit.wasm` into `public/`. On web, `index.web.js` loads CanvasKit before the app,
  because Skia binds to it when first imported. Pass style objects, not arrays, to `<Link asChild>` children.

Use Vitest for `physics/` and `tools/`. These modules are pure TypeScript, so they don't need jest-expo.
The unit tests run a coarse 0.5-step version of the no-direct-shot proof. Run `report.ts` before merging any
level or physics change.

## Build order

1. Scaffold the Expo app (TypeScript, Expo Router) around the existing `physics/`, `levels/` and `tools/`.
   Get `vitest` and `tsc` passing before any UI work.
2. Board rendering in Skia: grid, ground, fixed segments, glass, launcher, ball, trails.
3. Launch and path playback with Reanimated, driven by `useFrameCallback`.
4. Aim gesture, sliders, nudge buttons.
5. Piece tray and placement gestures (move and rotate) with react-native-gesture-handler.
6. Win flow, level select, progress saved with AsyncStorage.
7. Haptics on bounce and on landing (expo-haptics), plus sound.
